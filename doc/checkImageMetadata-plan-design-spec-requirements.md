## 1. Plan（計画概要）

### 1.1 背景

現行ツールは「先頭 64KB スキャン + 条件付きで末尾 128KB のバイト列スキャン」というヒューリスティクスで高速化しているが、その代償として構造的に取りこぼすメタデータが複数存在する。さらに JPEG / WebP の EXIF 解釈には、形式の異なるデータを前提関数に渡している等の実装レベルの誤りがある。本計画は、**PNG のチャンク構造・JPEG のセグメント構造・WebP の RIFF 構造という各形式本来の構造解析に置き換えることで、網羅性と速度を同時に改善する**ことを骨子とする。構造解析はヒューリスティクスより速い（IDAT 本体や画像データに触れずにヘッダだけを辿れるため）。

### 1.2 ゴール

- G1: §2 の欠陥一覧 D-01〜D-16、および §2 の追加欠陥表で処遇が「必須」とされた D-17〜D-26 を解消し、§11.3 のフィクスチャ行列をパスする（#41 は Phase 6 の P2 項目であり、Phase 6 を実施する場合に限る）。
- G2: PNG の検出範囲を「先頭 64KB + 末尾 128KB」から **ファイル全域相当** に拡張する。検出網羅性は全チャンクウォークと等価であること（例外は D-17 のみ）。実行経路は全ウォークではなく §7.1.5 の Negative-First とする。
- G3: WebP EXIF が実質常時空振りする現行状態を解消し、JPEG と WebP で同一の TIFF パーサを共用する。
- G4: XMP 経由のプロンプト / パラメータ（Draw Things、Midjourney、IPTC 2025.1 の AIPromptInformation）を取得可能にする。
- G5: Stealth PNG 検出経路の処理時間を、同一マシン比較で現行比 **1/2 以下**を目指す（目標値は NFR-PERF-03、施策は §9.1）。
- G6: 通常経路（Stealth を実行しない PNG / JPEG / WebP）の処理時間を現行より悪化させない（回帰 ±5% 以内）。

### 1.3 成功の定義

- §13 の受け入れチェックリストが全てチェック可能（自動テストまたは手順で検証可能）な形で満たされる。
- 既存の正常系サンプル（A1111 PNG、ComfyUI PNG、NovelAI PNG、A1111 JPEG、NovelAI WebP 等）の出力が、意図した追加分を除き変わらない。

追加の欠陥（第2次検討で発見したもの。「処遇」が各欠陥の扱いを定める）:

| ID | 優先度 | 処遇 | 内容 |
|---|---|---|---|
| D-17 | P1 | 必須（残存として明記 + `--strict`） | **IDAT チャンク間に挟まれたテキストチャンク。** PNG 仕様上 tEXt 等は IDAT 列の途中にも置ける。Negative-First の末尾チェーンは「最後の IDAT が IEND に接している」ことを確認するだけなので、途中に挟まったテキストは検出できない。FastWalk の二分探索は等間隔の崩れとして異常を検知し得るが、いずれの経路でも IDAT 間のレコードは記録されない（§7.1.5 の記録範囲規則）。実例は稀（通常のエンコーダは IDAT 列の途中に他チャンクを挟まない）だが、仕様書上で「既知の残存リスク」として明記し、`--strict`（IDAT 列を全て歩くモード）でのみ完全解消とする。デフォルトの網羅性主張はこの例外を伴うものとして README にも書く。 |
| D-18 | P2 | 必須 | **IEND より後ろの trailing data。** IEND 終端より後ろにバイト列が残っているファイル（ツールによっては JSON 等を付加する）が存在する。ファイルサイズ > IEND 終端位置の場合、その領域をテキストとして走査し、既知キーワード / JSON らしき内容があれば参考情報として出す。コストは trailing がある場合のみ発生する。 |

| D-23 | P2 | 記録のみ（実装しない） | **単体 TIFF ファイル（.tif / .tiff）。候補として記録のみ（本件では実装しない）。** TIFF パーサを作る以上、マジック `II*\0` / `MM\0*` の単体 TIFF を形式判定に追加すれば Photoshop / Lightroom 経由の生成画像で XMP (0x02BC) / UserComment を拾える見込みがある。ただし形式判定・見出し・JSON の `format` 値域等の周辺仕様の追加が必要なため、本件のスコープ（§3.1）には含めず、別件の候補として記録する。 |

| D-25 | P2 | 必須（退行防止の明記） | **WebP の RIFF サイズ不整合。** RIFF ヘッダのサイズフィールドが実ファイルサイズと一致しない（0 や過小の）出力をするエンコーダがある。ウォークの上限は RIFF サイズではなく実ファイル長を使うことを仕様として明記する（現行コードは実長を使っており正しい。リファクタ時に退行させない）。 |
| D-26 | P2 | 任意（P2） | **Base64 エンコードされた生成情報。** 一部ツールは JSON の生成情報を Base64 化してテキストチャンクや UserComment に入れる。本文全体が Base64 として妥当で、デコード結果が JSON / 既知キーで始まる場合に限り、デコードして表示する試行を追加する。無差別なデコード試行は誤検出の元なので、妥当性条件を厳しくする。 |

## 3. スコープ

### 3.1 スコープ内

- PNG: tEXt / zTXt / iTXt / eXIf / XMP iTXt の全域走査と解釈（§7.1）
- JPEG: セグメントウォーク、EXIF (TIFF) 構造解析、XMP / Extended XMP、COM（§7.3）
- WebP: RIFF ウォーク、EXIF を TIFF パーサで解釈、XMP（§7.4）
- EXIF/TIFF: LE/BE 両対応、IFD 構造解析、UserComment 文字コード処理の是正（§7.2）
- XMP: 要素テキスト形式からの抽出、Draw Things / Midjourney / AIPromptInformation 対応（§7.5）
- キーワード登録表の拡張（§7.6）
- Stealth PNG: 呼び出しポリシーのフラグ化と内部高速化（§7.7）。**インターレース以外**の現行対応範囲（署名4種、Alpha/RGB、8/16bit、カラータイプ 2/4/6、上限値）は維持する
- 高速化: §9 の各施策
- テスト: §11 の単体・統合・ゴールデン・性能回帰

### 3.2 スコープ外（実装しない）

- **Stealth PNG のインターレース（Adam7）対応** — 既知の非対応。本件では扱わない
- メタデータの**書き込み・削除・変換**機能（本ツールは読み取り専用）
- GUI / 拡張機能（AI Meta Viewer 等）との連携
- AVIF / HEIC / JPEG XL / GIF / BMP 対応（形式追加は別件とする）
- C2PA 署名の**検証**。C2PA マニフェストの**存在検出のみ** P2 として §7.8 に置く
- 画像ピクセル内容からの AI 判定（SynthID 等の透かし検出を含む）
- ネットワークアクセス一切
- **単体 TIFF ファイル（.tif / .tiff）対応**（D-23）と、**MP4 / MOV 等の動画・その他形式のメタデータ**（D-24）— いずれも候補として記録のみとし、本件では実装しない（詳細は §2 の D-23 / D-24）

## 4. 要件（Requirements）

### 4.1 機能要件 — PNG

| ID | 優先度 | 要件 |
|---|---|---|
| FR-PNG-01 | P0 | PNG の検出網羅性は、先頭から IEND までの全チャンクウォークと等価であること（例外は D-17: IDAT 間に挟まれたテキストチャンクのみで、`--strict` でのみ検出する）。実行経路は §7.1.5 の Negative-First（Stage A/B/C）とし、素朴な全ウォークは Stage C の最終フォールバックとしてのみ使う。検出範囲に 64KB / 128KB 等の固定上限を設けない（D-02, D-03, D-04 の解消）。 |
| FR-PNG-02 | P0 | zTXt を処理すること。キーワード（Latin-1）＋圧縮メソッドバイト（0 のみ有効）に続く zlib ストリームを解凍してテキストとして扱う（D-01）。 |
| FR-PNG-03 | P0 | tEXt / iTXt の既存対応を維持しつつ、iTXt のフィールド解釈を仕様通りにすること（§7.1.3）。 |
| FR-PNG-04 | P1 | eXIf チャンクを TIFF パーサ（§7.2）に渡し、UserComment / ImageDescription 等を取得すること（D-12）。 |
| FR-PNG-05 | P1 | キーワード `XML:com.adobe.xmp` の iTXt を XMP パーサ（§7.5）に渡すこと。 |
| FR-PNG-06 | P0 | チャンク長・オフセット計算は全て checked arithmetic とし、ファイル長を超えるチャンクは「そのチャンクを無効として走査終了」で処理し panic しないこと。 |
| FR-PNG-07 | P1 | 同一キーワードのチャンクが複数ある場合は全て出力すること（現行挙動の維持）。同一キーワード内では重複排除はしない。例外として、出典をまたいで本文が完全一致するレコードは D-21 の規則で1回に統合する。この「出典をまたぐ」には、チャンク種別（tEXt / zTXt / iTXt）が異なる場合を含む（詳細は §6.4）。 |
| FR-PNG-08 | P2 | ImageMagick / GIMP 形式の `Raw profile type exif` / `Raw profile type xmp`（16進エンコードされたプロファイル）テキストチャンクを検出した場合は、デコードして各パーサへ渡すこと。失敗時は生テキストを出さずスキップする。 |
| FR-PNG-09 | P1 | 署名（8バイト）が不正な入力は PNG として処理しないこと（現行の形式判定を維持）。CRC は検証しない（現行方針の維持。読み取り専用ツールであり、CRC 不一致でも読めるメタデータは読む）。 |

### 4.2 機能要件 — EXIF / TIFF

| ID | 優先度 | 要件 |
|---|---|---|
| FR-EXIF-01 | P0 | TIFF ヘッダを構造解析すること。バイトオーダー `II` (LE) / `MM` (BE) 両対応、マジック 42 の検証、IFD0 オフセットの取得（D-06）。 |
| FR-EXIF-02 | P0 | IFD エントリを型サイズ表に基づいて解釈し、値の総バイト数が 4 以下ならインライン値、超過ならオフセット先を読むこと（D-07）。 |
| FR-EXIF-03 | P0 | IFD0 に加え、ExifIFD ポインタ (0x8769) を辿って ExifIFD を解析すること。UserComment (0x9286) は通常 ExifIFD 側にある。IFD の再帰・循環は深さ上限 4 と訪問済みオフセット集合で防ぐこと。 |
| FR-EXIF-04 | P0 | 取得対象タグは最低限: UserComment (0x9286), ImageDescription (0x010E), Make (0x010F), Model (0x0110), Software (0x0131), Artist (0x013B), XPComment (0x9C9C, UCS-2LE), XMP パケット (0x02BC, 存在すれば XMP パーサへ)（D-10）。 |
| FR-EXIF-05 | P0 | UserComment の charset コードは先頭 8 バイト固定として処理すること（D-08）。詳細アルゴリズムは §7.2.3 に従う。先頭欠落が起きないこと。 |
| FR-EXIF-06 | P1 | UNICODE の LE/BE は BOM を最優先し、BOM が無い場合は BE/LE 両方で復号を試行し妥当性スコアで選ぶこと（D-09）。文字数上限は撤廃し、代わりにバイト長上限（§8.2）で制限すること。 |
| FR-EXIF-07 | P0 | タグのバイト列パターン検索（現行方式）を廃止すること。偶然の一致による誤検出が構造上起きないこと（D-07）。 |

## 6. Design（全体設計）

### 6.1 アーキテクチャ方針

1. **構造解析への統一**: 全形式を「コンテナをウォーク → メタデータブロックを発見 → 専用パーサで解釈 → 共通レコードとして出力」の流れに統一する。形式固有のバイト列検索は排除する（`memmem` の使用は XMP 拡張ヘッダ等の限定的箇所のみ許容）。
2. **共通レコード経由の出力**: パーサは直接 `println!` せず、レコードを出力層（Sink）へ渡し、出力層が整形する。レコードの具体的な受け渡し方式は §6.4 の定義（P-09）に従う。これによりゴールデンテストと将来の JSON 出力（FR-CLI-05）が可能になる。ただし現行の表示文言はレコードの `label` と `body` で再現する。
3. **TIFF パーサと XMP パーサの共用**: PNG eXIf / JPEG EXIF / WebP EXIF は全て TIFF パーサへ、PNG XMP iTXt / JPEG XMP / WebP XMP / TIFF 内 XMP (0x02BC) は全て XMP パーサへ集約する。

### 6.2 モジュール構成（提案）

```
src/
  main.rs        … CLI 引数処理、形式判定、出力層の呼び出し
  record.rs      … RecordView, Source, MetadataSink の定義（§6.4）
  output.rs      … テキスト整形 (BufWriter), (P2) JSON 整形
  png.rs         … PNG チャンクウォーク, tEXt/zTXt/iTXt 解釈
  jpeg.rs        … JPEG セグメントウォーク, APP1 振り分け, COM, Extended XMP
  webp.rs        … RIFF ウォーク
  tiff.rs        … TIFF/EXIF 構造解析, UserComment 復号
  xmp.rs         … XMP パケット抽出 (要素/属性, 実体参照, Draw Things 判定)
  keywords.rs    … PNG テキストキーワード登録表と見出しマッピング
  stealth.rs     … Stealth PNG (現行 check_stealth_png を分離し高速化)
  inflate.rs     … 上限付き解凍ヘルパ (zTXt / iTXt / Stealth で共用)
```

現行 `main.rs` 内の関数との対応: `extract_png_metadata` → `png.rs`、`parse_png_chunk` → `png.rs`、`extract_webp_metadata` → `webp.rs`、`extract_exif_metadata` / `extract_from_exif` → `jpeg.rs` / `tiff.rs` に分離、`check_stealth_png` 一式 → `stealth.rs`、`print_metadata` → `output.rs` + `keywords.rs`。

### 6.4 共通データモデル

データモデルは P-09（Visitor / スライス参照、§9.1）に基づく。本文を `String` でコピー保持する方式は、MB 級の workflow 本文を丸ごとコピーするため採用しない。レコードは入力バッファへのスライス参照で渡す形とする。

```rust
// record.rs
pub enum Source {
    PngText, PngExif, PngXmp, PngStealth,
    JpegExif, JpegXmp, JpegComment, JpegIptc,
    WebpExif, WebpXmp,
    TiffXmp,
    C2pa, Trailing,
}

// 本文は入力バッファへのスライスを基本とし、解凍・復号で生成した文字列のみ Cow::Owned になる
pub struct RecordView<'a> {
    pub source: Source,
    pub label: std::borrow::Cow<'a, str>,
    pub body: std::borrow::Cow<'a, str>,
    // §8.4 の keyword フィールド用。テキストチャンクではキーワード、それ以外では対象フィールド名
    pub keyword: Option<std::borrow::Cow<'a, str>>,
    // Stealth の mode / signature 等、出典の付随情報 (D-21 の出典併記にも使う)
    pub detail: Option<std::borrow::Cow<'a, str>>,
}

pub trait MetadataSink {
    fn on_record(&mut self, rec: &RecordView<'_>);
}
```

Source の割当表（コンテナ × ブロック → Source）: PNG tEXt/zTXt/iTXt（XMP 以外）→ `PngText`、PNG eXIf → `PngExif`、PNG iTXt の XMP → `PngXmp`、PNG Stealth → `PngStealth`、JPEG EXIF → `JpegExif`、JPEG XMP / Extended XMP → `JpegXmp`、JPEG COM → `JpegComment`、JPEG APP13/IPTC → `JpegIptc`、WebP EXIF → `WebpExif`、WebP XMP → `WebpXmp`、TIFF 0x02BC 経由の XMP → `TiffXmp`、TIFF 0x83BB 経由の IPTC → コンテナ側の Exif Source（`PngExif` / `JpegExif` / `WebpExif`）、C2PA 存在レコード（§7.8）→ `C2pa`、trailing data（§7.1.6）→ `Trailing`。
優先規則（入れ子の場合）: ブロック種別を優先する。すなわち、どのコンテナの EXIF 内であっても 0x02BC 経由で XMP パーサへ渡されたレコードは `TiffXmp` とし、コンテナ側の `PngExif` / `JpegExif` / `WebpExif` にはしない。PNG Raw profile（FR-PNG-08）経由で復号されたデータは、復号先のパーサに応じて通常の eXIf / XMP と同じ Source（`PngExif` / `PngXmp`）とする。

- 各形式のエントリ関数は `fn extract(input: &[u8], path: &str, opts: &Options, sink: &mut dyn MetadataSink)` の形に統一する。`input` はファイル全体を表すバッファ（mmap、または P-07 採用時は読み込み済みバッファ）であり、そのファイルの出力完了まで生存する。呼び出し側は次のファイルを処理する前に出力層を確定（flush）すること。
- 「メタデータなし」判定は Sink 側の受信件数（0件か）で行う（D-05 の `found` フラグ不整合はこの形でも構造的に消える）。
- テキスト出力用 Sink はレコードをファイル単位で Vec に集め（本文はスライス参照のままでコピーは発生しない）、flush 時に D-21 の重複排除を行ってから整形して書く。重複排除の規則: 既出本文の「長さ＋ハッシュ」集合で候補を判定し、完全一致をスライス比較で確認する。**統合は Source またはチャンク種別（`detail`）が異なるレコード間に限る。同一キーワード・同一種別の複数チャンクは統合せず、FR-PNG-07 通り全て出す。tEXt と zTXt は種別が異なるため、出典相違として扱う。** 統合時は**最初に出現したレコードを残し**（そのレコードの `label` と出現位置を使う）、残したレコードの本文末尾に改行を挟んで `(also in: <他出典の表示名>)` の行を出典ごとに1行ずつ追加する。表示名は `<§8.4 の source 文字列> <keyword>` で構成する（例: `also in: png_exif UserComment`）。統合される側のレコードが `keyword` を持たない場合（JPEG COM 等）は、表示名を source 文字列のみとする（例: `also in: jpeg_comment`）。`PngText` 由来のレコードは、実際のチャンク種別（tEXt / zTXt / iTXt）を `detail` に保持し、表示名では source 文字列の代わりにその種別を使う（例: `also in: zTXt parameters`）。JSON 出力用 Sink（P2）でも同じ重複排除を行い、表現は §8.4 の `sources` 配列に従う。
- `label` は完成した見出し文字列（例: Stealth の mode / signature を含む現行見出し文言）をパーサ側が構成して入れる。`detail` は JSON の `detail` フィールドに出力される付随情報であり、`label`（見出し）の構成には使わない。ただし D-21 の `(also in: …)` 表示名の構成には使う（`PngText` の場合は実際のチャンク種別が入る）。
- ゴールデンテスト用 Sink はレコードを所有文字列化して Vec に集め、期待文字列と比較する。

## 7. 詳細設計 — 形式別

### 7.1 PNG

#### 7.1.1 チャンクウォーク（FR-PNG-01）

```
cursor = 8  // 署名を検証済みであること
loop {
    if cursor + 8 > len { break }                       // ヘッダ不足で終了
    chunk_len = be_u32(mmap[cursor .. cursor+4]) as usize   // checked
    chunk_type = mmap[cursor+4 .. cursor+8]
    data_start = cursor.checked_add(8)
    data_end = data_start.checked_add(chunk_len)        // 溢れたら終了
    if data_end + 4 > len { break }                     // CRC 分まで存在すること
    data = mmap[data_start .. data_end]
    match chunk_type {
        b"tEXt" | b"zTXt" | b"iTXt" => handle_text_chunk(chunk_type, data),
        b"eXIf" => tiff::parse(data) をレコード化,
        b"caBX" => C2PA 存在レコード (§7.8),
        b"IEND" => break,
        _ => {}                                          // IDAT 等は中身に触れない
    }
    cursor = data_end + 4
}
```

- ウォーク自体のコストはチャンク数にのみ依存し、IDAT のバイト数に依存しない（NFR-PERF-01）。
- 途中のチャンクが破損（長さ超過）していたら、そこでウォークを打ち切り、それまでに得たレコードは保持する。
- APNG の追加チャンク（acTL / fcTL / fdAT）は無視してウォークを継続する（fdAT を IDAT と誤認しない）。

#### 7.1.2 tEXt / zTXt

- tEXt: 最初の NUL までがキーワード（Latin-1。バイト列をそのまま ASCII 範囲で照合）、残りが本文。本文は UTF-8 として妥当ならそのまま、妥当でない場合は Latin-1 → UTF-8 変換（各バイトを同コードポイントにマップ）して表示する。現行の「UTF-8 でなければ空文字」挙動は情報欠落なので改める。
- zTXt: キーワード + NUL + 圧縮メソッド1バイト（0 以外はスキップ）+ zlib ストリーム。解凍は上限付き（§8.2）で `inflate.rs` 経由とする。
- 解凍ラッパーの試行順序（D-19）: zlib → gzip → raw deflate の順に**全ラッパーを試行し**、解凍に成功したもののうち結果が UTF-8 として妥当なものを優先して採用する。UTF-8 妥当な成功がなければ、試行順で最初の成功を採用する（zTXt の本文は仕様上 Latin-1 であり、非 ASCII バイトを含む正規の本文は UTF-8 として妥当でないため、UTF-8 妥当性を採用の必須条件にしてはならない）。いずれも解凍に失敗したらそのチャンクをスキップする。
- 解凍後テキストの復号は tEXt と同じ規則（次項の UTF-16 判定 / UTF-8 → Latin-1）を適用する。
- tEXt 本文の UTF-16（D-20）: 本文先頭に BOM（`FF FE` = LE / `FE FF` = BE）がある場合は UTF-16 として復号する。BOM が無い場合は従来通り UTF-8 → Latin-1 の順で扱う。
- キーワード照合は §7.6 の登録表による。登録外キーワードは出力しない（現行方針）。

#### 7.1.3 iTXt（現行解釈の是正点を含む）

フィールド順は仕様通り: `keyword NUL | compression_flag(1) | compression_method(1) | language_tag NUL | translated_keyword NUL | text`。

- 現行コードの `data[null_pos + 3..]` 起点は結果的に正しいが、可読性のため各フィールドを順に読む実装に書き直すこと。
- `compression_flag == 1` の場合は text 部を解凍する（上限付き）。解凍の試行順序は §7.1.2 の D-19 の規則（zlib → gzip → raw deflate）に従う。`compression_method` が 0 以外はスキップ。
- フィールドが途中で欠落している（NUL が見つからない等）場合は、そのチャンクを無効としてスキップし、例外を伝播させない。
- キーワードが `XML:com.adobe.xmp` の場合は通常テキストとして出さず、XMP パーサへ渡す（FR-PNG-05）。圧縮 iTXt の XMP もあり得るため、解凍後に判定する。

#### 7.1.4 eXIf

- チャンクデータ全体が TIFF 構造（先頭がバイトオーダー）。JPEG の `Exif\0\0` プレフィックスは付かない点に注意し、TIFF パーサへそのまま渡す。

#### 7.1.5 チャンクウォーク自体の高速化（Negative-First、必須）【改訂版】

設計の主対象は「メタデータがある画像」ではなく「**AI メタデータを持たない大多数の画像**」である。持たない画像に対して「不在を証明するために全走査する」コストをいかに定数ページ数まで縮めるかが焦点であり、以下を §7.1.1 の素朴なウォークの前段に組み込むこと。素朴な全ウォークは最終フォールバックとしてのみ残す。

**コスト目標（不在ケース）**: 触れる範囲は「先頭チャンク群（Stage A、通常は先頭の数チャンク）＋末尾ウィンドウ W（初期値 128KB の定数）＋E0 確定の接続検証に伴う IDAT ヘッダプローブ分」以内に収まること。W は定数であり、ファイルサイズにも IDAT チャンク数にも依存しない（NFR-PERF-05）。この目標は Stealth 判定コストを含まない。Stealth を実行する経路の合算目標は §7.7.4（P-08）適用を前提に NFR-PERF-05 後段で定義する。

**Stage A: IDAT 前ウォーク**
- 先頭から通常ウォークし、最初の IDAT で停止する。ここは通常数チャンクで終わる。
- **早期終了はしない。** Stage A でメタデータが見つかった場合でも Stage B は必ず実行する（IDAT 前に `Description`、IDAT 後に `workflow` という配置があり、Stage A で止めると D-03 が再発するため。フィクスチャ #6）。見つからなかった場合は「不在候補」として Stage B へ進む（この時点では不在は未確定）。

**Stage B: 末尾チェーン解決（不在証明の本命）**
- 後置メタデータがある場合、そのチャンクは必ず「最後の IDAT の直後〜IEND の直前」の連続区間にある。逆に、**最後の IDAT が IEND の直前に直接接していることが確認できれば、後置メタデータの不在は IDAT 列を歩かずに証明できる**。
- 前段（IEND 位置の特定）: `E0 = len - 12` を無条件に IEND 開始と仮定しない。まず末尾 12 バイトが IEND チャンク（長さ 0 + `IEND` + CRC `AE 42 60 82`）と一致するか確認する。**末尾 12 バイトが一致した場合も、`len − 12` を無条件には確定せず、候補列の先頭（最優先候補）として下記の接続検証に回す**（trailing data として完全な PNG が付加された場合、末尾 12 バイトは trailing 側 PNG の IEND と一致してしまうため、検証なしでは誤確定し得る）。その検証に失敗した場合は、末尾 2MB 検索で得た候補列に合流させる。一致しない場合は、末尾 2MB の範囲で IEND チャンクのパターンを検索し、出現位置を候補とする。**試行する候補は出現順に最大 16 件まで**とし、上限を超えたら E0 未確定のまま Stage C へ進む。候補列は位置で重複排除する（最優先候補 `len − 12` が末尾検索でもヒットした場合は1回だけ試行する）。最大 16 件の上限には最優先候補も算入する。**候補は出現順（最も小さいオフセットから）**に試す: trailing data として完全な PNG が付加されている場合、主 PNG の IEND は trailing 側の IEND より先に現れるため、最後の出現を無条件に選んではならない。各候補の確定には、**Stage A のウォーク済みプレフィックスへの接続**を必須とする: 具体的には、Stage C 手順1 と同じ前方 IDAT ヘッダジャンプ／ウォークで Stage A の停止位置からその候補位置にチャンク境界として到達できることをもって確定とする（開始位置は Stage A の停止位置、ジャンプ上限 4096 回は候補ごとに適用する。コストは Stage B の予算に含める（NFR-PERF-05 第1文の「E0 確定の接続検証に伴う IDAT ヘッダプローブ分」。Stage C 側の上限には数えない）。総量は IDAT 数 × 試行した候補数に比例する）。チェーン解決（Stage B）の成否は候補の棄却理由にしない: チェーンがコスト制約（巨大 IDAT がウィンドウ外等）で未解決でも候補は棄却せず、その候補に対するエスカレーションとして扱う。**接続検証は到達可能性の確認のみであり、チャンク境界の走査に限定し、テキストチャンクの解析・レコード生成は行わない**（IDAT 間に挟まれたテキストチャンクをデフォルト経路で拾ってはならない。D-17 は `--strict` でのみ検出する原則を維持する）。候補が確定したら、後置区間の解決は従来通り Stage B チェーンで行う。ただし検証が IDAT ジャンプのみで候補に到達した場合（後置区間が存在しない場合）は、それをもって後置区間なしと確定し、Stage B チェーンは不要とする。接続を検証できた最初の候補を E0 として確定する。どの候補も接続を検証できなければ E0 未確定のまま Stage C へ進む（E0 未確定時の扱いは Stage C の共通規則に従う）。IEND より後ろの trailing data の走査は §7.1.6 の手順でチェーン解決後に行う。
- 手順: E0 を起点に、末尾ウィンドウ `W`（初期値 128KB、ファイル長で上限）の中で「`p + 12 + len(p) == E`（E は既知の次チャンク開始位置）を満たし、種別が下記ホワイトリストに含まれ、CRC32 が一致する」候補ヘッダ `p` を探し、直前チャンクを1つ確定する。
- ホワイトリスト（候補として受理するチャンク種別）: `IHDR`, `PLTE`, `IDAT`, `IEND`, `tEXt`, `zTXt`, `iTXt`, `eXIf`, `iCCP`, `sRGB`, `gAMA`, `cHRM`, `pHYs`, `tIME`, `sBIT`, `sPLT`, `tRNS`, `bKGD`, `hIST`, `sTER`, `acTL`, `fcTL`, `fdAT`、および先頭文字が小文字の補助チャンク全般（種別の1文字目が小文字 = ancillary のものは、長さ方程式と CRC が一致すれば受理する）。
- **IDAT の CRC は検証しない。** 直前チャンクが IDAT の場合、そのデータ長は W を超え得るため CRC 検証はコスト目標と両立しない。代わりに「長さ方程式の一致＋種別が `IDAT`＋`p` が Stage A の停止位置以降であること」で確定する。ただしこの確定は **IDAT ヘッダ `p` 自体がウィンドウ内にある場合に限る**。データ長が W を超える IDAT では `p` はウィンドウの外にあり、Stage B では候補にすらならない（そのケースは Stage B 前段の接続検証（前方 IDAT ヘッダジャンプ）で処理する。§11.4 の不在フィクスチャ (c) はこの経路で解決する想定であり、計測上は Stage B 終了に数える）。偶然の一致確率は長さ方程式（32bit 値の一致）と種別4バイトの同時成立で十分に低い。非 IDAT チャンクについては CRC32 一致を必須とする。**CRC32 の計算範囲は PNG 仕様通り「チャンク種別4バイト＋チャンクデータ全体」**とする（データのみで計算してはならない）。検証対象は最大でもそのチャンクのデータ長分で、テキスト系は通常小さい。
- **エスカレーション条件（重要）**: CRC 不一致、ホワイトリスト外の種別、長さ方程式を満たす候補が存在しない、のいずれも「不在確定」ではなく Stage C へのエスカレーション条件である。特に CRC が壊れた後置 tEXt（FR-PNG-09 は「CRC 不一致でも読めるメタデータは読む」方針）はチェーンでは確定できないため、必ず Stage C で拾うこと。
- 確定した直前チャンクについて繰り返す（チェーンを後方へ辿る）:
  - IDAT に到達したら、その時点でチェーン内の非 IDAT チャンクが後置区間の全構成である。チェーンで確定した非 IDAT チャンクは §7.1.1 ウォークと同等に**全種別を処理対象**とする（テキスト系チャンクの解析、eXIf → TIFF パーサ、iTXt の XMP → XMP パーサ、caBX → §7.8 の存在レコード）。メタデータ系チャンクが含まれていなければ「後置メタデータなし」が確定する。Stage A と合わせて不在が確定し、**IDAT 本体には一切触れずに終了**する。
  - メタデータ系チャンクに当たったら解析対象として記録し、さらに直前へ辿る（後置区間が複数チャンクの場合）。
  - Stage B の記録の処遇（Stage C へ移る場合）: Stage B の記録とチェーン先端は **Stage C 全体を通して保持（保留）する**。破棄が確定するのは手順1が成功して終了した場合のみである（手順1 のウォーク結果が後置区間全体をカバーするため、その時点で Stage B の記録を破棄する）。手順1が失敗して手順2へ進む場合は、保持した記録とチェーン先端のまま手順2が継続する（手順1→手順2 の遷移で Stage B が確定済みだった後置区間のチャンクを取りこぼしてはならない）。加えて安全策として、レコード収集時はチャンク開始オフセットをキーとして同一オフセットの二重記録を排除する。
  - 記録した後置チャンクは、出力前に**ファイル内オフセット昇順に並べ替えて**から解析・出力する（FR-CLI-03 の出現順原則。チェーンは後方へ辿るため発見順は出現順の逆になる）。
- 候補探索は、既知チャンク種別については多パターン検索（`memchr::memmem` を種別ごとに適用。§6.3）で候補位置を絞ってから長さ方程式と CRC を確認する。ホワイトリストの一般句（種別1文字目が小文字の未知の補助チャンク）は memmem では列挙できないため、それについてはウィンドウ内に限り、種別1文字目が小文字になる位置を候補として長さ方程式＋CRC を試す限定バイト走査を許す。**評価順序は全経路共通で「長さ方程式 → CRC」とし、方程式を満たさない候補には CRC を計算しない**（短絡評価。候補ごとに CRC を先に計算すると最悪 O(W²) 級になる）。これでも候補が確定しなければ Stage C へ進む。
- **チェーンの下限**: チェーンは Stage A の停止位置より前へは辿らない。到達したチャンクの種別で分岐する: 到達したチャンクが **IDAT であれば、それが Stage A の停止位置と一致する場合でも成功として終了する**（IDAT が1個だけの PNG では、チェーンで確定する IDAT のヘッダ位置は Stage A の停止位置そのものになるため）。IDAT でないチャンクの開始位置が停止位置と一致した場合は「未解決」として Stage C へ進む（Stage A 済みのチャンクの再記録を防ぐ）。
- **IDAT が存在しない場合**: Stage A は IDAT で停止せず IEND（または EOF）まで歩き終える。この場合 Stage A の時点で全域走査が完了しているため、Stage B / C は行わない。Stage A の「停止位置」はこの場合 IEND 開始位置（または len）とする。
- **Stage A がチャンク破損で打ち切られた場合**（最初の IDAT より前に長さ破損チャンクがある等）: Stage A の「停止位置」は破損チャンクの開始位置とする。この場合、接続検証と Stage C 手順1 は通常通り失敗し（停止位置から IDAT ジャンプは開始できない）、手順4 のフォールバックウォークが Stage A と同一の結果に帰着する（得られたレコードは §7.1.1 の規則通り保持する）。E0 は確定しないため trailing 走査（§7.1.6）は行わない。
- **候補の優先順位（同一の E に対して複数候補がある場合）**: 候補を全て列挙してから確定する。CRC 一致で検証できた非 IDAT 候補を、CRC を検証しない IDAT 候補より優先する。IDAT 候補でチェーンを終了してよいのは、他に検証済みの非 IDAT 候補が存在しない場合に限る（後置 tEXt のデータ内部に偶然現れた IDAT らしい位置で誤って終了し、後置メタデータを取りこぼすことを防ぐ）。さらに、**同一の E に対して CRC を計算したが不一致だった非 IDAT 候補が存在する場合は、IDAT 候補で終了せず Stage C へエスカレーションする**（CRC が破損した後置 tEXt、フィクスチャ #27 を IDAT らしい偶然位置で誤終了させないため）。

**Stage C: エスカレーション（少数ケースのみ）**
- Stage B でチェーンが解決しない場合に限り、以下の順で段階的に拡大する。**遷移規則は全段共通: 前の手順が「解決した」と判定した場合のみそこで終了し、解決しなければ次の手順へ進む。各手順の結果が検証に失敗した場合はその結果を破棄して次へ進む**（途中で探索全体を打ち切ってはならない）。
- **Stage C のウォークにおける記録範囲（D-17 の経路非依存化）**: Stage C の各手順のウォークでは、レコードは保留バッファに集め、IDAT に遭遇するたびに保留分を破棄し、IEND 到達時に残った保留分のみを記録として確定する。これにより、記録対象は実質的に「最後の IDAT の終端以降のチャンク」に限られ、IDAT 間に挟まれたチャンクはどの経路を通ってもデフォルトでは記録されない（D-17 は経路によらず `--strict` でのみ検出される）。手順4でウォークが IEND に到達せず終了した場合は、その時点の保留分を記録として確定させる（下記共通規則の「結果を保持する」方針に従う）。
- **E0 未確定時の共通規則**: Stage B 前段で E0 が確定しなかった場合、各手順の成功条件にある「E0 への到達」（手順3 の検証 (b) を含む）は「ウォークが IEND チャンクに到達した時点で、その位置を E0 として確定し、成功とみなす」と読み替える。**手順2（ウィンドウ拡大）は E0 未確定時は実施せず、手順3 へ進む**（チェーンの起点が存在しないため）。最終フォールバック（手順4）のウォーク結果は、E0 到達の成否にかかわらず §7.1.1 の規則通り保持する（途中で打ち切ってもそれまでに得たレコードは保持する）。
  1. **前方 IDAT ヘッダジャンプ（最初に試す）**: Stage A の停止位置（最初の IDAT のヘッダ位置）から、IDAT ヘッダの長さフィールドを使って `len + 12` ずつ前方へジャンプし、IDAT でないチャンクに到達したらそこから §7.1.1 の通常ウォークで IEND まで進む。各ジャンプで触れるのはヘッダのみ（IDAT データ本体には触れない）。単一〜少数 IDAT のファイル（例: 写真変換 PNG の単一巨大 IDAT）では1〜数回のジャンプで IDAT 直後に到達でき、即座に後置区間の有無が確定する。ジャンプ回数の上限は **4096回**（確定値）とし、超えたらこの経路を打ち切って手順2へ進む（E0 未確定時は共通規則により手順2を飛ばし手順3へ進む）。**成功条件: 通常ウォークが IEND 開始位置 E0 に到達すること。** 長さフィールドの破損等でウォークが E0 に到達せず途中終了した場合は、この経路の結果を破棄して手順2へ進む（E0 未確定時は手順3へ。末尾チェーン側で拾える後置メタデータを落とさないため）。
  2. ウィンドウ拡大: 「チェーン先端」を次のように定義する。先端は **確定済みチェーンの最小開始オフセット** とし、チェーンが1つも確定していない場合の初期値は E0 とする。手順2 の成功条件は Stage B のチェーン終了条件に準じる（IDAT への到達をもって成功とする。下限到達時の扱いは Stage B 本体の種別分岐に従う: 非 IDAT チャンクの開始位置が下限と一致した場合は未解決として次へ進む）。W は **E0 基準の到達距離**として定義する: 拡大後の到達範囲は `[E0 − 新W, E0)` であり、実際に新規に走査する区間は増分分 `[E0 − 新W, E0 − 旧W)` のみとする（先端が E0 から後方へ進んでいる場合もこの定義でギャップは生じない。チェーン側の記録との接続は先端位置で判定する）。拡大は W = 128KB → 512KB → 2MB の順で、累積コスト上限は合計 2MB とする（この 2MB は Stage B の初期ウィンドウ 128KB を含む累積値である。NFR-PERF-05）。単一チャンクが初期 W を超える場合（例: 200KB の workflow、フィクスチャ #4）はこの拡大でチェーンに取り込む。
  3. FastWalk 二分探索: IDAT 総数が3以上で、かつ最初の3個の IDAT が等長 `L` の場合にのみ試みる（IDAT が3未満の場合は 1. の前方ジャンプで処理できるため試みない。等長でない場合も試みない）。定義: `start` = 最初の IDAT のヘッダ開始位置、述語 P(k) = 「位置 `start + k*(L+12)` に IDAT ヘッダがあり、**かつ長さフィールドが L と等しい**」、探索範囲は k ∈ [0, floor((len - start) / (L+12))]。長さフィールドまで含めることで、この述語は完全長 IDAT の列に対して単調になり、二分探索で「最後の完全長 IDAT」を特定できる（長さを見ない述語では短い最終 IDAT も真になり区別できない）。**真の終端は格子点上にないことに注意する**: 通常のエンコーダでは最後の IDAT だけが短いため、候補位置を `候補 = 最後の完全長IDATのヘッダ位置 + 12 + L` と計算し、**候補位置のチャンクが IDAT であれば（それが短い最終 IDAT）、その長さフィールドでもう1ホップ進めて最初の非 IDAT チャンクの先頭を真の終端とする**（候補は短い最終 IDAT の先頭を指すため、そのままでは検証 (a) を満たさない）。単調性は前提として保証されないため、計算した終端位置の検証は次の両方を必須とする: (a) 終端位置が非 IDAT チャンクの先頭であること、(b) 終端位置から通常ウォークで E0 までチャンク境界が連続して正確に到達できること。(a) だけでは IDAT 列途中の整列した境界からでも E0 に到達してしまうため不十分で、(b) だけでも終端の正しさは証明しない。両方を満たさなければ結果を破棄して手順4へ進む。
  4. 最終フォールバックは IDAT 専用タイトループ（IDAT ヘッダだけを辿る）を経て §7.1.1 の通常ウォーク。
- エスカレーションは例外経路であり、大多数の不在画像は Stage B までで終わること。エスカレーション発生率は性能フィクスチャ（§11.4）の不在ケース PNG 3種で計測し、PR に記録する（§13 の受け入れ項目）。

**残存リスクとモード**
- デフォルトでは Stage C まで自動エスカレーションするため、網羅性は D-17 の例外を除き全ウォークと同一に保たれる。
- `--fast-exit` フラグは設けない（FR-CLI-02）。Stage B で打ち切るモードは採用しない。
- `--strict` 指定時は Stage A/B/C を使わず、IDAT 列を含む全チャンクを §7.1.1 のウォークで辿る（D-17 の完全解消）。

**実装上の注意**
- チャンク種別比較はバイト列比較ではなく u32（ビッグエンディアン読み）同士の整数比較にする。CRC32 は `crc32fast`（§6.3、P-11）を使い、検証対象は末尾チェーンの非 IDAT チャンクに限る。通常経路で全チャンクの CRC を検証してはならない。
- JPEG / WebP は本節の対象外: JPEG のメタデータは SOS 前のセグメントに限られセグメント数も少なく、WebP も画像データチャンクが少数であるため、不在ケースでも構造ウォーク自体が元々定数オーダーに近い。PNG の IDAT 分割だけが特殊である。


#### 7.1.6 IEND 後の trailing data（D-18）

- 対象: IEND チャンク終端位置より後ろにバイトが残っている場合のみ。その領域を最大 **1MB** まで走査する（§8.2。それを超える trailing は先頭1MBのみが対象で、残りは検査しない。これは既知の制限として明記する）。
- 実行タイミング: trailing 走査は、到達経路（Stage B / Stage C の各段 / `--strict` の全ウォーク）によらず、**IEND 終端位置が確定した後に必ず**行う。trailing が 2MB を超えて IEND が末尾検索で見つからない場合は、Stage C のフォールバックウォークで IEND に到達した時点で終端位置が確定し、そこから走査する。
- 判定と本文の切り出し（**JSON 形式を先に試み、成功した場合はキーワード形式を適用しない**。trailing の JSON は内部に登録キーワード `prompt` 等を含み得るため、両形式のレコードが二重に生成されることを防ぐ）:
  - trailing 領域が PNG 署名（`89 50 4E 47 0D 0A 1A 0A`）で始まる場合は、キーワード形式の対象外とする（付加された PNG 内部のチャンクのキーワードを誤検出しないため。フィクスチャ #38）。
  - JSON 形式: 領域の先頭（空白を除く）が `{` で始まる場合、ストリーミング JSON パーサ（`serde_json::StreamDeserializer`）で先頭の値1つを読み、読み取りに成功したら消費したバイト範囲を本文とする（後ろにゴミが続いていてもよい）。この場合 `keyword` フィールドは省略する。
  - キーワード形式: 領域内に §7.6 登録キーワードのいずれかが現れた場合、レコードの本文は「キーワードの直後から、最初の NUL または領域末尾まで」とする。本文にキーワード自体は含めない。キーワード直後が区切り文字（NUL / `=` / `:`）の場合はその区切りも除く。キーワードが見つかった場合はそのキーワードを `keyword` フィールドに入れる。複数キーワードがある場合はキーワードごとに1レコードとする。
  - どちらでもなければ無出力。
- 表示: 見出しは `Trailing Data (after IEND)`、Source は `Trailing`（§6.4）。
- 通常のチャンク解析とは別枠であり、trailing 内の内容を通常メタデータと同格の見出しで出してはならない。

### 7.2 TIFF / EXIF パーサ

#### 7.2.1 構造解析

1. 入力: TIFF バイト列の開始位置。呼び出し側の責務として、コンテナ固有のプレフィックスを除いた位置から渡すこと: JPEG APP1 では識別子 `Exif\0\0`（6バイト）を除いた位置、WebP EXIF と PNG eXIf ではプレフィックスなしでチャンク先頭（単体 TIFF ファイルの対応は本件の対象外。D-23）。XMP の場合も名前空間文字列（NUL 終端まで）を除いた位置から XMP パーサへ渡す（§7.3.1）。
2. バイトオーダー: `[0..2]` が `II` なら LE、`MM` なら BE。それ以外は空の結果を返す。
3. マジック: u16 で 42 を確認。IFD0 オフセット: u32 を読み、範囲内であることを確認。
4. IFD 解析: エントリ数 u16、各エントリ 12 バイト（タグ u16 / 型 u16 / 数 u32 / 値またはオフセット u32）。
5. 型サイズ表: 1=BYTE:1, 2=ASCII:1, 3=SHORT:2, 4=LONG:4, 5=RATIONAL:8, 6=SBYTE:1, 7=UNDEFINED:1, 8=SSHORT:2, 9=SLONG:4, 10=SRATIONAL:8, 11=FLOAT:4, 12=DOUBLE:8, 13=IFD:4。未知の型はそのエントリをスキップ。
6. 値の総バイト数 = 型サイズ × 数（checked_mul）。4 以下なら値フィールド先頭から、超過なら u32 オフセット先（TIFF 開始位置からの相対）から読む。全て境界チェックする。
7. ExifIFD ポインタ (0x8769) があれば辿る。深さ上限 4、訪問済みオフセットを記録して循環を防ぐ。GPSInfo ポインタ (0x8825) と Interoperability ポインタ (0xA005) は、先に本書の表示対象タグが存在しないため**辿らない**（将来拡張）。
8. IFD エントリ列の直後にある「次 IFD オフセット」(u32) を読み、0 でなければ IFD1 として**常時**解析対象とする（サムネイル用だが表示対象タグが入っている場合がある。コストはエントリ数分のみ）。IFD1 の先（IFD2 以降）は辿らない。IFD1 のオフセットが訪問済み集合に登録済みの場合は再解析しない（ExifIFD と同じオフセットを指す細工等による二重解析を防ぐ）。**IFD1 内の ExifIFD ポインタ (0x8769) は辿らない。** 次 IFD オフセットの追跡は **IFD0 からの1回のみ** とし、ExifIFD および IFD1 の次 IFD フィールドは無視する（§7.2.2 の走査順 IFD0 → ExifIFD → IFD1 を崩さない）。

#### 7.2.2 取得タグと表示

| タグ | 名称 | 見出し | 処理 |
|---|---|---|---|
| 0x9286 | UserComment | `EXIF UserComment` | §7.2.3 の復号。結果が A1111 形式らしい（`Negative prompt:` または `Steps:` を含む）場合も見出しは `EXIF UserComment` のまま本文をそのまま出す。JSON の場合は整形を試みる（FR-EXIF-08） |
| 0x010E | ImageDescription | `EXIF ImageDescription` | ASCII / UTF-8 として表示。A1111 の JPEG では本タグに parameters が入ることがあるため、UserComment と同格に扱う |
| 0x0131 | Software | `EXIF Software` | 1行表示 |
| 0x010F / 0x0110 | Make / Model | `EXIF Make` / `EXIF Model` | それぞれ1行表示（1タグ = 1レコード） |
| 0x013B | Artist | `EXIF Artist` | 1行表示 |
| 0x9C9C | XPComment | `EXIF XPComment` | UCS-2LE として復号し表示 |
| 0x02BC | XMLPacket (XMP) | （XMP パーサ側で決定） | バイト列を XMP パーサへ渡す |
| 0x83BB | IPTC-NAA | `IPTC Caption (EXIF)` | P2: Caption/Abstract (2:120) のみ取得 |

- レコード粒度は **1タグ = 1レコード** とする。Make と Model も分離する。
- 表示対象タグが複数ヒットした場合はタグ番号順ではなく **IFD 内の出現順** に出す。IFD を跨ぐ場合は走査順（IFD0 → ExifIFD → IFD1）とする。

#### 7.2.3 UserComment 復号アルゴリズム（FR-EXIF-05, FR-EXIF-06）

UserComment の先頭 8 バイトは文字コード識別子である。**値のバイト数が 8 未満の場合は、コード識別子なしとして全体を ASCII/UTF-8 として扱う**（下記 `_` 分岐と同じ。`data[0..8]` を無条件に切って panic してはならない）。

```
code = data[0..8]; body = data[8..]
match code {
  b"ASCII\0\0\0"   => body を UTF-8 (妥当でなければ Latin-1 変換) として表示。末尾 NUL は除去
  b"JIS\0\0\0\0\0" => **Shift_JIS 復号は実装しない**（§14.1 の決定）。body が UTF-8 として妥当なら UTF-8 として表示し、妥当でなければ Latin-1 変換してそのまま表示する。encoding_rs 等のデコーダ依存は追加しない
  b"UNICODE\0"     => UTF-16 として §7.2.4 で復号
  [0,0,0,0,0,0,0,0] => 未定義。まず §7.2.4 の UTF-16 判定 (BOM または NUL パターン) を試み、
                      当たらなければ ASCII として扱う
  _                 => code を含め全体を ASCII/UTF-8 として扱う (先頭8バイトを捨てない)
}
```

- 重要: 現行 D-08 の分岐（先頭4バイトが 0 のときに本文を `[12..]` から取る）は削除する。本文開始位置の規則は分岐ごとに固定する: `ASCII` / `JIS` / `UNICODE` / 未定義（全0）の各分岐では本文は常に 8 バイト目から（`body = data[8..]`）。全体を使うのは `_` 分岐（コード自体が上記のどれにも一致しない場合）のみで、その場合は先頭8バイトも含めて全体を ASCII/UTF-8 として扱う。

#### 7.2.4 UTF-16 判定

1. BOM: `FF FE` → LE、`FE FF` → BE。BOM 自体は出力に含めない。
2. BOM が無い場合: BE 復号と LE 復号の両方を試行し、スコアで選ぶ。スコア = 制御文字（U+0000〜U+0008, U+000E〜U+001F）の少なさ + 置換文字 U+FFFD の少なさ。ASCII 範囲の文字が多い方を優位とする簡易規則でよい。
3. 末尾の U+0000 は除去する。途中の U+0000 で打ち切らない（現行の `take_while(|&c| c != 0)` は、本文中の NUL で早期終了するため改める。ただし連続する末尾 NUL の除去は行う）。

### 7.3 JPEG

#### 7.3.1 セグメントウォーク

不変条件: **`pos` は常にセグメント先頭の `0xFF` の位置を指す**。セグメント全体の長は `2 + seg_len`（マーカー2バイト + 長さフィールドを含むセグメント長）である。

```
pos = 2  // SOI (2バイト) を検証済み。pos は次のセグメントの 0xFF 位置
loop {
    if pos + 2 > len { break }                        // マーカー (2バイト) の最小残量
    if mmap[pos] != 0xFF { break }                    // 想定外の位置ではウォーク終了 (走査継続しない)
    while pos + 1 < len && mmap[pos+1] == 0xFF { pos += 1 }  // フィラー 0xFF を読み飛ばす。pos は最後の 0xFF を指すよう更新し、以降の長さ計算はこの pos を基準とする
    if pos + 2 > len { break }                        // フィラー消費後に再チェックする
    marker = mmap[pos+1]
    match marker {
        0xDA (SOS) | 0xD9 (EOI) => 終了,
        0xD0..=0xD7 | 0x01      => { pos += 2; continue },   // 長さフィールドなし
        _ => {
            if pos + 4 > len { break }                // 長さフィールド (2バイト) の残量を先に確認する
            seg_len = be_u16(mmap[pos+2 .. pos+4])    // 長さフィールド自身 (2バイト) を含む値
            if seg_len < 2 { break }                  // 不正値では前進できず無限ループするため終了 (NFR-SEC-01)
            if pos + 2 + seg_len > len { break }      // スライス取得より前に checked で範囲を確認する
            payload = mmap[pos+4 .. pos+2+seg_len]
            match marker {
                0xE1 => 先頭識別子で振り分け (下記),
                0xFE => COM として記録,
                0xED => Photoshop IRB (FR-JPEG-05, §7.3.3),
                0xEB => C2PA 存在検出 (§7.8),
                _ => {}
            }
            pos += 2 + seg_len
        }
    }
}
```

APP1 (0xE1) の振り分けと、パーサへ渡すスライスの開始位置:
- ペイロードが `Exif\0\0` で始まる場合: TIFF パーサへは **6バイトを除いた** `payload[6..]` を渡す。
- ペイロードが `http://ns.adobe.com/xap/1.0/\0` で始まる場合: XMP パーサへは名前空間文字列（NUL を含む）以降を渡す。
- Extended XMP の場合も同様に、名前空間文字列以降を §7.3.2 のヘッダとして読む。
- **最初の APP1 で止めない。** EXIF APP1 と XMP APP1 は別セグメントとして両方存在し得るため、SOS まで全セグメントを見る（D-22）。
- COM の見出し: 内容が A1111 形式らしい（`Negative prompt:` または `Steps:` を含む）場合は `Stable Diffusion (A1111)`、それ以外は `JPEG Comment` とする（FR-JPEG-04）。

- エントロピー符号化データ内に現れる `FF 00` は SOS 以後の話であり、ウォークは SOS で止まるため考慮不要。
- 例外の明記: プログレッシブ JPEG では複数スキャン間に APPn / COM が挿入され得るが、本仕様では最初の SOS までを対象とし、スキャン間のセグメントは対象外とする（生成系メタデータは通常先頭側に置かれるため実害はほぼない）。

#### 7.3.2 Extended XMP の再構成

- ヘッダ: 名前空間文字列（`http://ns.adobe.com/xmp/extension/\0`。実装時は定数をこの仕様文字列リテラルから生成し、バイト長を別途ハードコードしない）、続いて GUID (ASCII 32文字)、全長 u32 BE、この断片のオフセット u32 BE、断片本体。
- 断片をオフセット順に連結して1つの XMP パケットとして解析する。主 XMP が存在しない場合でも断片だけで解析を試みる。
- 再構成のタイミング: 拡張断片はセグメントウォーク完了までバッファし、主 XMP の解析後に検証・再構成を行う（主 XMP の APP1 が拡張断片より後に現れる配置でも `HasExtendedXMP` 照合ができるように）。GUID の照合は16進表記の大文字・小文字を区別しない。
- 妥当性検証と上限: (1) 宣言された全長が §8.2 の XMP 上限（16MB）を超える場合は、断片を確保せず Extended XMP 全体をスキップする（上限は宣言全長の時点で効かせる）。(2) 全断片の GUID（MD5）と宣言全長が一致することを確認する。一致しない断片が混ざっている場合は再構成を諦める（異なる拡張パケット由来の断片の混在を検出するため）。主 XMP が存在する場合は、主 XMP の `xmpNote:HasExtendedXMP` の値と断片 GUID の一致も確認し、不一致なら再構成を諦める（主 XMP が存在しない場合は現行通り断片のみで試行する）。`HasExtendedXMP` の照合は (名前空間 URI `http://ns.adobe.com/xap/1.0/note/`, ローカル名 `HasExtendedXMP`) で行い、通常は属性形式で書かれているため属性形式で抽出する。(3) 各断片について `オフセット + 断片長 ≤ 宣言全長` を確認し、断片同士の区間が重なっていないこと（同一オフセットの重複を含む）を確認する。重なりがある場合は再構成を諦める。(4) 断片にギャップ（欠落）がある場合、または連結後の長さが宣言全長と一致しない場合は再構成を諦め、主 XMP のみを解析する。主 XMP が存在しない場合は断片を使わない。

#### 7.3.3 Photoshop IRB / IPTC の最小形式仕様（FR-JPEG-05）

APP13 のペイロードは識別子 `Photoshop 3.0\0`（14バイト）で始まる。続く Image Resource Block (IRB) の列を以下の構造で読む:

- IRB: 署名 `8BIM` (4バイト) + リソース ID u16 BE + 名前（Pascal 文字列: 1バイト長 + 本体、全体を偶数バイトにパディング）+ データサイズ u32 BE + データ（偶数バイトにパディング）。
- リソース ID `0x0404` が IPTC (IIM) データである。
- IIM レコード: タグ `0x1C` + レコード番号 u8 + データセット番号 u8 + データ長 u16 BE（最上位ビットが立つ場合は拡張長形式: 下位15ビットが後続の長さバイト数）+ データ。
- データセット **2:120** が Caption/Abstract。本文として表示する。見出しは `IPTC Caption` とする。文字コードはレコード1のデータセット **1:90**（Coded Character Set）が宣言する: 値が UTF-8 を示す場合（例: `ESC % G`）は本文を UTF-8 として扱い、それ以外の宣言または宣言なしの場合は UTF-8 → Latin-1 の順で扱う。（注: 2:100 は Country/Primary Location Code であり文字コードとは無関係なので参照しない）
- 構造が途中で破損していたら、その時点で IRB ウォークを打ち切り、それまでに得た分は保持する。

### 7.4 WebP

- RIFF ヘッダ検証（現行維持）後、チャンクをウォークする: FourCC 4バイト + サイズ u32 LE + 本体 + パディング（サイズが奇数のとき1バイト）。**ウォークの上限は RIFF ヘッダのサイズフィールドではなく実ファイル長とする**（D-25。サイズフィールドが 0 や過小なエンコーダ出力がある。現行コードは実長を使っており正しいので退行させない）。
- `EXIF` → TIFF パーサ（FR-WEBP-01）。WebP の EXIF には `Exif\0\0` プレフィックスは無い。
- `XMP ` → XMP パーサ（FR-WEBP-03）。
- `C2PA` チャンクがあれば §7.8 の存在レコードを出す。
- VP8X の EXIF/XMP フラグは信頼せず、実チャンクの有無で判定する。

### 7.5 XMP パーサ

#### 7.5.1 方針

XMP は RDF/XML で、同一内容でも直列化形式が書き手によって異なる（要素形式 / 属性形式、`rdf:Alt` の有無、プレフィックス名の違い）。完全な XML パーサなしで堅牢にやるため、以下の方針とする:

- 照合は **(名前空間 URI, ローカル名)** で行う（FR-XMP-01 が規範）。プレフィックス文字列は書き手ごとに変わるため、パケット内の名前空間宣言（`xmlns:接頭辞="URI"`）を先に収集して接頭辞→URI の対応表を作り、要素名・属性名の接頭辞を URI に解決してから §7.5.2 の対応表と照合する。対象 URI: description / title は `http://purl.org/dc/elements/1.1/`、UserComment は `http://ns.adobe.com/exif/1.0/`、CreatorTool は `http://ns.adobe.com/xap/1.0/`、HasExtendedXMP は `http://ns.adobe.com/xap/1.0/note/`、DigitalSourceType / AIPromptInformation は `http://iptc.org/std/Iptc4xmpExt/2008-02-29/`。名前空間宣言が見つからない要素は対象外とする（ローカル名だけでの照合はしない）。
- 抽出は3系統を用意する:
  1. **要素形式**: `<prefix:LocalName ...> ... </prefix:LocalName>` の内側を取り、`rdf:Alt/rdf:li` 構造があれば FR-XMP-05 の規則で1件選ぶ。内側に更に要素があればテキストノードを連結する。
  2. **属性形式**: `prefix:LocalName="..."` または `prefix:LocalName='...'` の属性値を取る。
  3. **rdf:resource 形式**: 対象要素の開始タグ内にある `rdf:resource="..."` 属性の値を取る（例: `<Iptc4xmpExt:DigitalSourceType rdf:resource="http://cv.iptc.org/newscodes/digitalsourcetype/trainedAlgorithmicMedia"/>` のような空要素形式。DigitalSourceType の代表的な直列化であり、要素形式・属性形式のどちらでも取得できないため必須とする）。
- **同一フィールドの重複排除**: 同一の (名前空間 URI, ローカル名) が複数の系統、または複数の `rdf:Description` ブロックから取得可能な場合は、**要素形式 → 属性形式 → rdf:resource 形式** の順に最初に取得できた値を採用し、1パケットにつき1フィールド1レコードとする（同一 Source 同士の重複は §6.4 の D-21 統合の対象外のため、ここで排除する）。
- 取得した生文字列には必ず実体参照デコード（FR-XMP-04）と CDATA 展開を適用する。
- 実装方式は正規表現クレートの新規導入を避け、バイト列走査で実装する。`quick-xml` は原則として導入しない（§6.3）。例外的に導入する場合も、抽出規則は本節の定義に従うこと。

#### 7.5.2 フィールド対応表

| フィールド (名前空間:ローカル名) | 意味 | 表示見出し | 備考 |
|---|---|---|---|
| `dc:description` | 説明。Draw Things では A1111 形式テキスト、Midjourney ではプロンプト一式 | `XMP Description` | FR-XMP-02, FR-XMP-03。Draw Things 判定時は §7.5.3 の確定規則により非表示。Midjourney 判定時は §7.5.3 により見出しが `Midjourney (XMP)` になる |

#### 7.5.3 Draw Things 判定と表示

- 条件: `exif:UserComment` の復号後テキストが `{` で始まり JSON として parse 可能で、キー `c` を含む。
- 表示項目（存在するものだけ）: プロンプト `c`、ネガティブ `uc`、モデル `model`、LoRA `lora`（配列: model 名と weight）、サンプラー `sampler`、CFG `scale`、シード `seed`、seed_mode、shift、steps、ガイダンス等の追加キーは、未知キーも含め JSON の整形表示を併記して情報を落とさないこと。
- `dc:description` の扱い（確定規則）: UserComment JSON の解析に成功した場合、`dc:description` は表示しない（Draw Things では description は JSON の `c`/`uc` 等から再構成された A1111 形式テキストであり、同じ情報の二重表示になるため）。UserComment が JSON でない、または解析に失敗した場合は、`dc:description` を通常の XMP Description レコードとして表示する。この規則をフィクスチャ #8 で固定する。
- レコード粒度: Draw Things の表示項目は全体で **1レコード**（複数行の本文）とする。
- Midjourney 判定（FR-XMP-03）の確定規則: XMP パーサ自体は `dc:description` を通常の Description レコードとして出す。「他に SD 系メタデータがない場合」の判定は、ファイル全体のレコードが揃う **flush 時**に Sink 側で行う: Description レコードがあり、SD 系レコードが1件もない場合に、そのレコードの見出しを **`Midjourney (XMP)`** に置き換える（確定文言）。それ以外の場合は見出しは `XMP Description` のままである。SD 系レコードの範囲（確定）: §7.7.1 の `auto` 判定で数える Source を持つレコードのうち、当該 Description レコード自体と、**パケットを問わず当該ファイル中の全ての CreatorTool / DigitalSourceType レコード**（FR-XMP-07 のフォールバック）を除いた全て（SwarmUI / InvokeAI / AIPromptInformation のレコードを含む）。パケット単位の区別は Sink からは判定できないため行わない。

### 7.7 Stealth PNG

#### 7.7.1 実行ポリシー（FR-STL-01）

| モード | 挙動 |
|---|---|
| `auto`（デフォルト） | 通常メタデータが0件の場合のみ実行（現行互換・高速性優先）。「通常メタデータ」の数え方: Sink が受信したレコードのうち、通常パーサ由来のもの（`PngText`, `PngExif`, `PngXmp`, `JpegExif`, `JpegXmp`, `JpegComment`, `JpegIptc`, `WebpExif`, `WebpXmp`, `TiffXmp`。FR-XMP-07 の CreatorTool/DigitalSourceType のみのフォールバックレコードも含む）を数える。`C2pa`（存在レコード）と `Trailing` は数えない。判定時点は Sink 受信時とし、D-21 の重複排除は行う前の件数で判定する |
| `always` | 通常メタデータの有無にかかわらず実行（D-15 の完全解消はこちら） |
| `never` | 実行しない |

#### 7.7.2 ビット読み取りのイテレータ化（FR-STL-02）

- 現行 `read_stream_byte` はビットごとに `pixel_index / height`、`% height`、チャンネル計算、checked 演算、`decoded.get()` を行っている。これを、**列優先順序（pixelIndex = x * height + y）を逐次たどるカーソル構造体**に置き換える:
  - カーソル状態: `x, y, channel_idx, row_start, sample_offset` を保持し、1ビット進むごとに増分更新する。除算・剰余は初期化時以外で使わない。
  - **16bit サンプルのオフセット規則（必須）**: 16bit の場合は各サンプルの **2バイト目（offset+1）の LSB** を読む（現行コードの `sample_offset = 1` 相当。拡張機能互換の規則であり、イテレータ化後も維持すること。offset 0 で実装すると 16bit Stealth が無言で壊れる）。8bit の場合は offset 0。
  - 参照先バイト位置は増分で計算し、境界チェックは行開始時にまとめて行う（行データが範囲内であることは IDAT 展開後の検証で保証済みの前提をコメントに明記する）。**この保証前提は全量展開経路でのみ成立する。** インクリメンタル経路（§7.7.4）では、判定時点では展開が完了していないため、その行が実際に復元済みであることを行単位で確認してからイテレータへ渡すこと（NFR-SEC-01）。
- ヘッダ 152 ビット（署名 15 バイト + 長さ 32 ビット）→ 署名照合 → ペイロード、という2段構えは維持する（FR-STL-03）。

#### 7.7.3 フィルタ復元と展開（FR-STL-05, S-03）

- フィルタ復元は行ごとに `filter` 値で分岐し、5種それぞれの専用ループで処理する。現行のバイト単位 `match` と `Option::map` クロージャを排除する。`left / above / upper_left` の取得はスライス参照で直接行う。
- `flate2` の feature を `zlib-ng` に変更し、IDAT 展開を高速化する。feature 構成の規範は §6.3（feature 変更でビルドが通らない環境向けに miniz_oxide へ戻せる構成にし、README に注記する）。
- IDAT チャンク参照の収集（現行 `Vec<&[u8]>` + `PngIdatReader`）はゼロコピーのため維持する。

#### 7.7.4 インクリメンタル早期判定（P-08、必須）

- 署名判定に IDAT 全量の展開を要しない。zlib デコーダをストリーミングで回し、ヘッダ 152 ビットの判定に必要な行数分（列優先で x=0 列: Alpha 約152画素分 / RGB 約51画素分の行）だけを展開・フィルタ復元した時点で署名を判定し、不一致なら即座に中止する。一致した場合のみ、進行中の展開をそのまま継続して全量処理する（再展開しない）。
- **適用条件とコスト**: この短縮が効くのは画像の高さが必要画素数（Alpha 152 / RGB 51）を超える場合のみである。コストは概ね「必要行数 / 画像の高さ」倍に縮むが、高さがそれ以下の小さい画像ではヘッダ判定にほぼ全行が必要で効果はほぼない。その場合の高速化はイテレータ化・フィルタ専用ループ化（P-03 / P-04）側で担保する。
- **行の検証**: 判定に使う各行は、実際に復元が完了していることを確認してから読む（§7.7.2 の保証前提は全量経路限定）。
- **バッファリング要件**: 復元済みの先頭行は、署名判定に必要な範囲をバッファに保持すること（サイズは「1行のバイト数 × 必要行数」で決まる。幅が大きい画像では相応に大きくなるため上限は設けず、必要行数分のみ保持する）。現行コードは同一バッファに対して Alpha → RGB の順に署名を試すが、ストリーミング化で Alpha 不一致と判定した時点では RGB 判定に必要な先頭行は既に通過している。保持したバッファに対して両モードを判定し、二重展開を避けること。
- 本施策は Phase 4 の必須範囲とする（NFR-PERF-05 の Stealth 合算目標の前提）。

### 7.8 C2PA（P2、存在検出のみ）

- PNG: `caBX` チャンクの存在を検出したら `C2PA manifest present` の1行レコードを出す。
- JPEG: APP11 (0xEB) セグメント内の JUMBF に `c2pa` が含まれれば同様。
- WebP: `C2PA` チャンクがあれば同様。
- マニフェスト内部の解析・署名検証はしない。

## 8. Specification（入出力仕様）

### 8.1 入力

- 対象: ローカルファイル1件（P2 で複数件）。形式はマジックバイトで判定: PNG 署名8バイト / `RIFF....WEBP` / JPEG `FF D8 FF`。
- ファイルサイズ 0 バイト〜 mmap 可能な範囲。空ファイルや途中までしかないファイルでも panic しない。

### 8.2 サイズ上限（解凍・表示）

| 対象 | 上限 | 超過時の挙動 |
|---|---|---|
| tEXt 本文 | 制限なし（ファイルサイズが上限） | — |
| zTXt / 圧縮 iTXt の解凍後 | 64 MB / チャンク | そのチャンクをスキップ |
| XMP パケット | 16 MB | そのパケットをスキップ |
| EXIF ブロック全体 | 16 MB（コンテナ側のサイズが実質上限） | そのブロックをスキップ |
| 個別タグ値（UserComment 等） | 所属する EXIF ブロック全体の上限に準ずる（単独の文字数上限は設けない。FR-EXIF-06） | そのタグをスキップ |
| Stealth 各種上限 | 現行値を維持（FR-STL-04） | 現行通り None |
| trailing data の走査（D-18） | 1 MB | 先頭1MBのみ対象とする |

### 8.3 終了コード

| コード | 条件 |
|---|---|
| 0 | 処理完了（メタデータの有無を問わない。現行維持） |
| 1 | 引数不正（未知フラグを含む）、ファイルオープン失敗、mmap 失敗 |
| 1 | （P2・複数ファイル時）1件でも処理に失敗したファイルがあれば 1。ただし残りのファイルの処理は継続する |

### 8.4 JSON 出力スキーマ（P2、FR-CLI-05）

```json
{
  "file": "path/to/image.png",
  "format": "PNG",
  "records": [
    { "source": "png_text", "keyword": "parameters", "label": "Stable Diffusion (A1111)", "body": "..." },
    { "source": "png_xmp", "keyword": "exif:UserComment", "label": "Draw Things (XMP)", "body": "..." }
  ]
}
```

- `format` は `PNG` / `JPEG` / `WebP` / `Unknown`。レコードが無い場合は `records: []`。
- `source` の変換表（§6.4 の Source 定義から）: `PngText` → `"png_text"`、`PngExif` → `"png_exif"`、`PngXmp` → `"png_xmp"`、`PngStealth` → `"png_stealth"`、`JpegExif` → `"jpeg_exif"`、`JpegXmp` → `"jpeg_xmp"`、`JpegComment` → `"jpeg_comment"`、`JpegIptc` → `"jpeg_iptc"`、`WebpExif` → `"webp_exif"`、`WebpXmp` → `"webp_xmp"`、`TiffXmp` → `"tiff_xmp"`、`C2pa` → `"c2pa"`、`Trailing` → `"trailing"`。
- `keyword` フィールドは、出典がテキストチャンク系（`PngText`）の場合はそのキーワード、それ以外の場合は対象フィールド名を入れる。フィールド名は書き手の接頭辞に依存させず、§7.5.2 の対応表の**正規化表記**（例: `exif:UserComment`, `dc:description`）で入れる。**キーワードもフィールド名もない場合は、フィールド自体を省略する（`null` は使わない）。** TIFF 由来レコードの `keyword` はタグ名（例: `UserComment`, `ImageDescription`）で入れる。JPEG COM のレコードでは `keyword` は省略する。IPTC 由来レコード（`JpegIptc`、および TIFF 0x83BB 経由）の `keyword` は `Caption/Abstract` とする。`C2pa` レコードでは `keyword` は省略する。
- `detail` フィールド（任意）: RecordView の `detail` をそのまま入れる。内容は出典により異なる: Stealth の場合は mode / signature、`PngText` の場合は実際のチャンク種別（`tEXt` / `zTXt` / `iTXt`）。なければ省略する。
- D-21 で統合されたレコードは、`source` に最初に出現した出典を入れ、統合された全出典を `sources` 配列に入れる。`sources` は `{ "source": ..., "keyword": ..., "detail": ... }` のオブジェクト配列とし、**最初に出現した出典を先頭要素として含む**（`source` フィールドと重複するが、出典の完全な一覧はこちらで保持する）。`keyword` がない出典ではその要素の `keyword` は省略し、`detail` は出典レコードに `detail` がある場合のみ入れる（`PngText` のチャンク種別等、テキスト出力の `(also in: …)` 表示名が保持する情報量と揃える）。統合されていないレコードでは `sources` は省略する。

## 10. エラー処理方針

- パーサ内部の失敗は「そのブロック / チャンクをスキップして継続」が原則。現行の `Result<_, Box<dyn Error>>` を `?` で最上位まで伝播させる方式は、1チャンクの破損で全体が落ちるため、PNG ウォーク内では使わない。
- ファイルオープン / mmap の失敗のみが終了コード 1 の対象。
- 標準出力への書き込み失敗（パイプ切断等）は無視して終了してよい。

## 11. Test 計画

### 11.1 単体テスト（バイト列合成方式）

各パーサに対し、テストコード内で最小バイト列を組み立てて検証する:

- TIFF: LE / BE の両方で、UserComment（インライン値になる短い値 / オフセット値になる長い値）、ImageDescription、ExifIFD ポインタ経由の UserComment、**表示対象タグが IFD1 にのみ存在するケース**、**ExifIFD の次 IFD フィールドが非0でも辿らないケース**、循環オフセット、範囲外オフセット。
- UserComment 復号: ASCII コード、未定義コード（全0）、UNICODE + BOM LE / BOM BE、BOM なし LE（ASCII 多め）、本文中に NUL を含むケース、先頭が日本語のケース、**バイト数が8未満（空・短い値）で panic せず全体が表示されるケース**。本文先頭4バイト欠落（D-08）が起きないことを明示的にassertする。
- XMP: 要素形式 / 属性形式 / **rdf:resource 形式**（DigitalSourceType が空要素 + `rdf:resource` 属性で書かれたケース）、**同一フィールドが要素形式と属性形式の両方（または複数の `rdf:Description`）に存在する場合に要素形式が優先され1レコードになるケース**、`rdf:Alt` の x-default 選択、実体参照（名前付き・10進・16進）、CDATA、Draw Things JSON、Midjourney description、AIPromptInformation。
- PNG テキスト: tEXt（UTF-8 / Latin-1）、zTXt（正常 / 圧縮メソッド異常 / 解凍上限超過）、iTXt（非圧縮 / 圧縮 / フィールド欠落）。
- JPEG ウォーク: EXIF と XMP が両方ある場合の振り分け、COM、SOS 以後に偽 APP1 バイト列があっても拾わないこと、**0xFF フィラーがマーカー前に連続するケース**（長さフィールドの読み位置がずれないこと）。**複数 APP1**（EXIF APP1 と XMP APP1 が別セグメントで共存し、最初の APP1 で止まらないこと。D-22）、**Extended XMP の再構成**（複数断片をオフセット順に連結、主 XMP なしで断片のみ）、**APP13/IPTC**（IRB を辿って 2:120 が取れること。§7.3.3）。
- Negative-First（PNG）: 末尾チェーンで後置 tEXt を発見できること、CRC が壊れた後置 tEXt ではチェーン確定せず Stage C へエスカレーションして検出できること、単一巨大 IDAT（W 超）では Stage B 前段の接続検証（前方 IDAT ヘッダジャンプ）で E0 が確定し解決できること、IEND 後に trailing data がある場合はその手前でチェーンが解決すること、**IEND 後に完全な PNG が付加された場合に E0 が主 PNG の IEND に確定すること（末尾12バイトが trailing 側 IEND と一致しても接続検証で切り分ける）**、**二分探索経路**（手順3へ到達する構成を明示する: 等長 IDAT を 5000 個持ち前方ジャンプの上限 4096 回を超えること、かつ末尾チェーンが解決しないこと — 例として後置区間が 2MB を超えてウィンドウ拡大でも解決しない構成にする。この合成 PNG で、二分探索の検証が成功するケースと、検証に失敗して結果が破棄されタイトループに落ちるケース。あわせて「最後の IDAT だけが短い」構成で、候補位置から1ホップ進めて真の終端が得られるケース）。

### 11.4 性能フィクスチャ

- PNG: 10MB の IDAT を持ち末尾に workflow を持つ ComfyUI 相当ファイル（現行テールスキャンとの比較用）
- PNG: Stealth 埋め込み済み 2048×2048 RGBA（Stealth 経路の比較用）
- JPEG: 5MB、EXIF あり（通常経路の回帰用）
- **PNG（不在ケース、Negative-First 検証用）**: メタデータなし PNG 3種 — (a) スクリーンショット相当（多数の小 IDAT、テキストチャンクなし）、(b) ブラウザ canvas 相当の出力、(c) 写真変換 PNG（単一巨大 IDAT を含む）。各々で Stage B で終了するか、Stage C へエスカレーションするかを計測し、エスカレーション発生率を PR に記録する。(c) は構造上 Stage B のチェーンでは解決せず、前段の接続検証（前方ジャンプ。単一 IDAT なら1回）で解決する想定であり、計測上は Stage B 終了に数える。

- 各フェーズは個別 PR とし、フェーズをまたぐ変更を混ぜない。コミット規約は以下とする:
  - **粒度**: PR 内のコミットは欠陥 ID（D-xx）または施策（P-xx / S-xx）単位で分け、対応するフィクスチャのテストを同じコミットに入れる（テストと実装を別コミットに分けると中間状態でテストが赤くなり、`git bisect` が使えなくなる）。
  - **各コミットで緑を維持**: どのコミットでも `cargo build --release` と `cargo test` が通る状態にする（回帰が出た際に bisect で混入コミットを特定できるようにするため）。
  - **Phase 0 は実装変更ゼロ**: ゴールデンテストと計測記録のみとし、実装コードは変更しない（以降の全フェーズの回帰判定の基準点になるため）。
  - **リファクタと振る舞い変更の分離**: モジュール分割等の「移動のみ」の変更は、ゴールデンテスト無変更で通過する単独コミットにし、欠陥修正と混ぜない。
  - **コミットメッセージ**: 先頭に ID を付ける。例: `D-01: zTXt チャンクの読み取りに対応 (fixture #2)`、`P-09: MetadataSink / RecordView を導入`、`Phase 0: ゴールデンテストと現行性能の計測値を追加`。
- Phase 1 と Phase 2 は TIFF パーサの受け口（Phase 1 で eXIf を呼ぶ先）で依存するため、Phase 2 の TIFF パーサ骨格（IFD 解析なしの最小実装）を Phase 1 に前倒ししてもよい。その場合は Phase 1 側の独立コミットとして明示すること。

## 14. リスクと決定事項

### 14.1 本書で決定済み（Codex が再判断しないこと）

| 論点 | 決定 |
|---|---|
| PNG CRC | 検証しない。壊れた CRC でも読めるメタデータは読む |
| Stealth のデフォルト | `auto`（現行互換）。完全網羅は `--stealth always` で opt-in |
| 登録外キーワード | 出力しない（ノイズ防止）。汎用メタデータ表示モードは本件で作らない |
| XMP パーサ | 軽量抽出（バイト列走査）が原則。`quick-xml` は原則として導入しない（§6.3） |
| 画像デコード系クレート | 導入禁止（§6.3） |
| Shift_JIS 専用デコーダ | 導入しない。§7.2.3 のフォールバックで済ませる |

### 14.2 リスク

| リスク | 影響 | 緩和 |
|---|---|---|
| XMP の直列化バリエーションが想定より多い | 一部ツールで抽出漏れが残る | （名前空間 URI, ローカル名）照合 + 要素/属性/rdf:resource の三系統抽出（§7.5.1）+ 取得できない場合の CreatorTool/DigitalSourceType フォールバック（FR-XMP-07）。漏れた実サンプルがあればフィクスチャに追加して直す運用にする |
| zlib-ng のビルド環境依存（C コンパイラ必須） | 一部環境でビルド失敗 | Cargo feature で miniz_oxide に戻せる構成にし、README に明記する |
| ゴールデンテストが現行のバグ込み出力を固定してしまう | Phase 0 で誤った期待値を固定 | ゴールデンは「現行で正しく出ていたケース」のみに限定し、欠陥ケースは修正後の期待値で新規に書く |
| TIFF の循環・巨大オフセット等の悪性入力 | panic / ハング | 深さ上限・訪問済み集合・全て checked arithmetic（FR-EXIF-03, NFR-SEC-01）で担保し、malformed フィクスチャで検証する |
